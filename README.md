# 工业园区通勤班车预约、迟到申诉与晚点考勤豁免平台

Vue 3 + Element Plus（前端）/ NestJS + TypeORM（后端）/ PostgreSQL（数据库）。
前后端合并为单个镜像：NestJS 同时提供 API 与前端静态资源，`docker compose up -d` 一键部署。

---

## 原始需求

### 本次需求（晚点考勤豁免，原文）

增加晚点考勤豁免。班车因道路事故晚到园区时，平台根据 GPS、站点签到、到厂时间和企业规则生成迟到证明。HR 确认后，受影响员工考勤状态、司机绩效和线路复盘一起更新。证明生成后，员工端和 HR 端看到同一晚点原因，减少人工截图传递。迟到证明还会标明影响企业和班次，便于 HR 批量处理。批量处理结果会回写考勤系统。

### 本次需求（站点施工临时改站 + 企业加班补车，原文）

增加站点施工临时改站。某站点因道路施工无法停靠时，平台推荐临时站点、步行距离和通知范围。员工确认后，司机导航、乘车名单和未确认人员提醒同步变化。临时站点会显示安全上车点和步行路线，司机端导航也要同步变化。未确认员工会进入司机点名提醒，防止改站后漏接。司机点名会保留未上车原因、站点时间和员工确认。增加企业加班补车。某企业临时加班到深夜时，HR 发起补车申请，平台检查车辆、司机工时、员工人数和费用承担。补车完成后，企业账单和员工乘车记录进入月结。补车费用会按企业、人数和司机工时拆分，进入园区月度结算。补车完成后，司机休息时间也会重新计算，避免连续超时驾驶。超时驾驶会触发调度提醒和司机休息校验。

### 本次需求（企业搬迁线路重排与员工代表确认，原文）

增加企业搬迁后的线路重排与员工代表确认。企业搬迁或新增厂区时，平台先冻结原线路的新预约，把受影响班次、站点、在乘员工、司机工时、车辆座位和费用分摊列出来，按新厂区位置、员工居住分布、现有线路走向和道路条件生成候选线路，标明每站步行距离、预计到厂时间、班次衔接和是否需要跨区接驳。园区不能直接切换线路，需把候选方案发给企业HR和员工代表，员工代表按站点、班次、步行距离和到厂时间反馈意见，HR汇总企业侧生产排班要求，园区运营调整后形成正式方案，再由企业负责人和员工代表确认生效。生效前保留旧线路过渡期，已预约员工可改站、改班次或退订，未确认的员工继续按旧站点乘车并收到提醒，避免漏接。搬迁导致原有站点取消的，平台标记站点停用日期，司机端和员工端同步更新，门禁和考勤规则按新厂区重新匹配。若新线路运力不足、司机工时超限、跨区接驳费用增加或企业间费用分摊有争议，平台把员工、司机、调度、企业HR和园区运营放在同一线路调整单中处理，先确认费用承担和班次安排，再锁定座位和车辆。旧线路停用后，历史乘车记录、考勤豁免、补车费用和申诉仍按原线路档案保留，新线路从生效日期起独立结算。线路重排结果、员工代表意见、企业确认人和生效时间进入园区线路档案，后续线路优化和费用争议可回查。

### 平台初始需求（原文）

建设工业园区通勤班车预约与迟到申诉平台，可采用 Vue 3、NestJS 和 PostgreSQL。员工按企业、班次、站点、上下班时间、是否携带行李和临时加班提交预约，平台根据车辆座位、线路、司机、站点容量和企业考勤规则生成乘车名单。司机发车前确认车辆、路线、乘客签到和临时空座；员工上车时扫码或刷工牌，迟到、未到、临时改站和代刷会被记录。若道路拥堵、车辆故障、站点施工、员工错过班车、企业临时加班、司机绕行或班车到厂晚点，平台要把员工、司机、调度、企业 HR 和园区运营放在同一趟车里处理。到厂后，实际到达、迟到原因、考勤豁免、补车费用、司机绩效和员工申诉进入档案，用于优化线路和企业考勤协同。平台还要处理多企业共线、节假日调休、夜班员工、临时访客、园区门禁和司机安全培训。班车晚点不只是交通问题，还会影响考勤、生产排班和员工满意度。园区还要处理多班倒、跨区接驳、极端天气停运、临时安检和企业搬迁，线路优化需要持续影响车辆、司机和企业费用。线路调整结果还要给企业负责人和员工代表确认，防止通勤优化只由园区单方决定。

## 一、快速启动（宿主 Docker）

```bash
cp .env.example .env        # 可按需修改 CC_PUBLISH_PORT（默认 3081）
docker compose up -d --build
docker compose ps           # web 健康检查变为 healthy 后访问
```

浏览器访问：

```
http://<宿主IP>:<CC_PUBLISH_PORT>/           # 例如 http://localhost:3081/
```

- 前端页面与 API 同源（API 前缀 `/api`），PostgreSQL **不发布到宿主端口**，仅在 compose 内网通过服务名 `db` 访问。
- 健康检查：`GET http://<宿主IP>:<CC_PUBLISH_PORT>/api/health`
- 容器首次启动会自动建表（TypeORM synchronize）并写入幂等演示数据（`seed` 重复启动不会覆盖数据）。
- 查看实际映射端口：`docker compose port web 3000`
- 停止并清理：`docker compose down`（保留数据卷加；连数据一起删：`docker compose down -v`）

## 三、推荐业务流验证脚本（浏览器点一遍）

1. 用 `dispatcher` 登录 → **调度派车**：对“东线早班”点“生成名单”（可先不选车，系统自动匹配座位；指派 `driver01`）。
   观察：按站点排座、多企业费用分摊、超载 overflow 分流提示；员工与司机均收到站内通知。
2. 用 `driver01` 登录 → **司机控制台**：勾选车辆/路线检查 → 开放签到；
   用“扫码/工牌”输入 `HX1001`、`HX1002` 签到；对某乘客做“改站”“代刷登记”；留 1 人不签到直接“发车”（自动记未到）→ “到厂确认”。
3. 到厂后：系统按企业宽限规则生成考勤（实际到达/迟到分钟/迟到原因/补车费）、司机绩效（晚点扣分、满载奖、故障/绕行罚则），并推送通知。
4. 用任意角色在 **途中事件协同** 上报“道路拥堵/车辆故障/极端天气…”，调度或运营处理时选择“考勤豁免/补车费园区承担/退费”，相关考勤档案自动联动改写，员工与 HR 收到结果通知。
5. 用 `emp_li` 登录 → **我的考勤/申诉** 对迟到记录发起申诉；用 `hr_huaxing` 在 **迟到申诉** 页“成立 + 豁免 + 退费”或“升级运营”，考勤与费用自动更新。
6. **线路调整完整双确认**：运营发起提案 → 东线三家共线企业 HR（`hr_huaxing`/`hr_ruifeng`/`hr_hengxin`）各自确认 → 三家员工代表（`emp_li` 李磊 / `emp_zhao` 赵强 / `emp_zhou` 周婷）各自确认；缺任一方运营发布都会被拒绝（可用 `emp_xu` 普通员工验证 403）；矩阵完整后运营“发布执行”一次落地，重复发布被幂等拒绝。
7. **访客与门禁**：HR 登记访客生成 `V-` 码 → 访客乘车核验 → 门禁页刷访客码/工牌入园、离园；错误凭证、过期访客码会被拒绝并留痕。
8. **极端天气停运**：调度对车次“停运”→ 全车员工/司机/HR/运营收到停运通知，考勤统一豁免。
9. **基础数据**：维护企业考勤规则、线路站点（标记施工会通知调度）、夜班/接驳班次、车辆状态、节假日调休/停运日。
10. **晚点考勤豁免（本次新增，推荐重点验证）**：
    - 昨日事故证明开箱即处理：`hr_huaxing` 登录 → 晚点豁免证明 → 打开 `LATE-<昨日>-0001`，可看到四类取证（GPS 轨迹/站点扫码签到/到厂时间/企业宽限规则）→ 选择企业×班次「批量确认豁免并回写考勤」→ 3 条考勤转豁免、补车费清零，司机 driver01 绩效撤销晚点扣分（非司机责任），线路复盘自动生成整改措施；员工 `emp_li` 端看到同一晚点原因与「已豁免回写」。
    - 今日实时链路：调度走完一趟「名单→签到→上报道路事故事件→到厂」后，到厂时平台自动取证生成证明（也可在「晚点豁免证明」页点「平台取证生成证明」手工发起）；证明按**企业 × 班次**标明影响范围，多企业共线时各企业 HR 分别批量确认（瑞丰 HR 无法处理华星员工，越权 403）；全部确认后证明闭环。
    - 驳回路径：HR 可对本企业批次驳回并填写原因，员工收到通知后仍可走迟到申诉。
11. **站点施工临时改站**：调度在「施工临时改站」选无法停靠站 → 系统推荐同线路临停点（步行距离/安全上车点/路线）→ 通知受影响员工；员工在「班车预约」页顶部确认/反馈无法前往，名单上车站点同步；司机控制台导航卡片展示临停点与未确认人员，可逐人点名（已上车/拒改站/未到），保留原因、站点时间与确认状态，防止漏接。
12. **企业加班补车**：HR 在「加班补车/月结」发起深夜补车（自动费用预检）→ 调度派车派司机（车辆、当日累计驾驶工时、强制休息窗口硬校验；`driver04` 当日已 260 分钟会被 300 分钟上限拦截）→ 司机发车/送达完成（按实际工时重算费用、重置休息时间、超时通知调度）→ 运营在「月度结算」按企业/人数/工时出账，企业账单与员工乘车记录进入月结。
13. **企业搬迁线路重排**：运营在「搬迁线路重排」发起（自动冻结原线新预约并盘点班次/站点/在乘/工时/座位/分摊）→ 生成 3 个候选（直达/东环/跨区接驳，含步行/到厂/衔接）→ 员工代表（如华星 `emp_li`）按站点/班次/步行/到厂反馈、HR 汇总排班 → 运营先锁费用承担（有争议拒绝）再锁座位车辆 → HR 企业确认 + 员工代表确认双确认 → 生效落地独立新线、旧站写停用日期、未选择员工继续旧站乘车并提醒；历史考勤/补车/申诉按原线保留。种子内置恒信搬迁至滨湖智造园的「意见征集」演示单（含 2 个候选与代表意见），登录 `hr_hengxin`/`emp_zhou` 查看。

### 晚点考勤豁免（本次新增）需求点对照

| 需求 | 实现位置 |
|---|---|
| 班车因道路事故晚到园区 | 事件类型含 `accident`/`congestion`；到厂车次 GPS 实际到厂晚于计划到厂即判定晚点 |
| 平台根据 **GPS、站点签到、到厂时间、企业规则** 生成迟到证明 | `POST /api/late-certificates/generate`：**写入前统一核验闸门**——① 车次已到厂且同时具备 GPS 实际到厂与计划到厂时间戳，按二者重算晚点（不采信手工填写分钟）；② 必须关联**同一趟车**留痕的外部事件（事故/拥堵/天气/施工/管制/故障），纯手工原因说明或引用他车事件一律拒绝；③ 存在已扫码签到员工；④ 实际晚点达到平台阈值（10 分钟）**或**超过任一受影响企业宽限规则。任一不满足即 4xx 回滚，证明/考勤/费用/绩效/复盘/通知零写入；到厂自动触发（`maybeAutoGenerate`）走同一闸门，准点车次静默不出证。证据汇总 GPS 离场/到厂时间与轨迹摘要、逐人站点签到、计划 vs 实际到厂、各企业宽限/上班时间/扣款规则存为 `evidence` |
| **HR 确认** | HR/运营在「晚点豁免证明」页按批次确认（`batch-confirm`）或驳回（`batch-reject`），行锁串行化并发处理 |
| **公共晚点与个人迟到分责** | 证明从站点签到/到厂事实把晚点拆为 `commonLateMinutes`（GPS 车次公共晚点，事故可豁免）与 `personalLateMinutes`（发车后补签到等个人到站迟到，不随事故豁免）；HR 确认时无个人责任者整条豁免+费用清零，含个人迟到者仅豁免事故部分，个人部分按企业宽限/扣款结算为可申诉迟到；证明影响名单、回写、通知、绩效、复盘分别保留两类分钟 |
| **标明影响企业和班次，便于批量处理** | 证明 `impactSummary.companies[]` 按「企业 × 班次」聚合（人数、超宽限人数、原补车费）；影响名单 `LateCertificateAffected` 逐人落库；HR 可选定单个企业/班次一键批量 |
| 确认后**受影响员工考勤状态**更新并**回写考勤系统** | 批次事务内回写对应 AttendanceRecord：无个人责任者改 `exempt`、`exempt=true`、补车费清零；含个人到站迟到者改 `partial_exempt` 语义（事故公共分钟写入 `exemptReason`，个人分钟按宽限判定保留 `late`/`normal` 与扣费，`lateReason=personal`），统一回写 `lateReason/certificateId`，员工即时收到分责通知 |
| **司机绩效**一起更新 | 非司机责任原因（事故/拥堵/天气/施工等）撤销**事故公共晚点**扣分：安全分恢复 100、罚款清零并备注证明编号；员工个人发车后补签到不纳入事故影响、不虚增受影响人数；责任相关原因维持考核；同步通知司机 |
| **线路复盘**一起更新 | 证明生成即建 `LineReview`（根因与证明同源）；全部企业确认后转「已复盘」，分别统计事故整条豁免 `exemptedCount` 与分责保留个人迟到 `partialExemptCount`，自动生成整改措施（重点监控、缓冲时刻、区间车、账单核销、企业准点提醒），运营/调度可补充 |
| **员工端和 HR 端看到同一晚点原因**，减少人工截图 | 晚点原因在证明生成时固化为单一 `reasonText` 字段，员工端「我的考勤→晚点考勤豁免证明」与 HR 端详情渲染同一字段（E2E 有一致性断言） |
| 权限隔离 | HR 只见/只处理本企业证明与员工（跨企业 403）；员工仅见本人受影响证明；非相关角色不可生成/批量处理 |

| 按新厂区/居住分布/走向/道路生成候选，标明步行/到厂/衔接/跨区 | `POST /:id/options` 确定性生成 3 方案（直达北延/东环绕行/跨区接驳），每站 `walkMeters/arriveTime/transferNote`、班次衔接、`crossDistrict` 与月增费 |

| 代表按站点/班次/步行/到厂反馈，HR 汇总排班 | `POST /:id/feedback`（verdict + 站点/班次/步行/到厂/意见）、`POST /:id/hr-summary` |

| 企业负责人 + 员工代表确认生效 | `confirm-company` → `company_confirmed` → 员工代表 `confirm-employee` → `confirmed`（代表提前确认 400）；**双确认时即生成新线骨架但 `openedFrom=effectDate`（生效日前不可约）**，运营只能在生效日当天/之后 `effectuate` 切换 |
| 按 effectDate 分离确认/预约切换/旧线停用，防止双线双约 | 新线 `openedFrom` 之前预约接口拒绝；旧线在重排进行中冻结、生效日后旧站（closedFrom）拒新约；**同一员工同日同方向仅一条待乘预约**（已完成行程不冲突）；同一旧线只允许一张进行中重排单 |
| 旧线过渡期、已预约改站/改班次/退订、未确认继续旧站并提醒 | `POST /:id/choose`（keep_old/change_station/change_schedule/refund）：改站/改班做目标容量与同日同向去重，同一预约最终选择只允许一次，退订释放座位且明确不计费；生效时未选择员工自动 keep_old 并 critical 提醒 |
| 站点停用日期、司机端员工端同步、门禁考勤按新厂匹配 | 生效时旧站写 `closedFrom/closeReason`、旧线 suspended；新线路/站点/班次独立创建；前端预约对停用日期后的旧站拒绝 |
| 旧线档案保留、新线生效日起独立结算 | 生效仅新建新线，不改动历史预约/考勤/补车/申诉；新线 `code=L-NEW-x`、独立班次与后续结算；旧线历史档案可查 |
| 结果/意见/确认人/生效时间入园区档案 | 重排单保留 `feedbacks/choices/companyConfirmById/effectiveById/effectiveAt`，`GET /:id` 可回查 |
